## 2. Executive Summary

Indian subscription/D2C merchants lose recurring revenue to payment failures (UPI, cards, e-mandates/NACH). Today they respond with either silence (revenue leaks) or dumb blast messaging (revenue leaks **plus** annoyed customers). Razorpay's own recovery tooling exists but is described publicly at one-line depth; the buildathon bar demands measured recovery, stopping rules, and audit trails — which no thin shipped blurb demonstrates.

Reflex is a merchant-side agent on top of **Razorpay test-mode APIs**: it ingests failure events, classifies each into a **canonical root cause** (rules first, LLM only for the ambiguous tail), scores every candidate intervention by **expected value** (propensity × amount − channel cost − annoyance penalty), passes every action through a deterministic **Shield** guardrail module, executes via retries / payment links / simulated channels (WhatsApp, SMS, email, Hinglish voice), observes outcomes, applies its versioned policy (versioning built: v1 frozen priors; v2 trainer written, not yet run), and **stops or escalates** when rules or EV say so. Every decision is written to a **hash-chained action ledger**.

Value is proven on a **pre-registered, reproducible evaluation**: 3,000-episode synthetic replay, three arms (do-nothing, tuned naive, Reflex), ablations, bootstrap confidence intervals, one-command reproduction. Simulation results are always labeled as simulation.

**Design principle (say it in every pitch):** *AI proposes, deterministic code disposes.* The LLM never authors an amount, link, deadline, or authorization.

## 3. Problem Statement

**Exact problem.** A material share of payment attempts and recurring-debit mandates fail (card declines, UPI failures, eNACH/UPI AutoPay mandate failures). Merchants either don't follow up or follow up indiscriminately. Recovery today is manual, unsophisticated, unmeasured, and often customer-hostile.

**Who experiences it.** Indian subscription & D2C merchants on Razorpay; their ops/finance staff; and their customers (who get either silence or spam).

**Why existing workflows are insufficient.**
- Gateway-level retries re-attempt the same rail; they don't change channel, timing, or message, and don't reason about root cause.
- Bulk SMS/email blasts ignore root cause, annoy customers (complaints, opt-outs, DND violations), and are never measured against a baseline.
- Manual ops (export CSV → agency → pray) doesn't scale, isn't auditable, and can't optimize cost-per-recovery.
- Global dunning tools (Stripe Smart Retries, ChurnBuster, Recurly, Baremetrics Recover) are card-rail + English-first; they don't model UPI failure modes, mandate lifecycles, salary-cycle timing, or vernacular outreach. *(Vendor landscape: [VERIFIED] these products exist; India-rail gap: [ASSUMPTION] based on public product pages — re-verify before citing in pitch.)*

**Why it matters financially.**
- Involuntary churn from failed payments is a documented, large loss category; industry benchmarks place full retry+dunning recovery around 50–70% of failed value, leaving large amounts unrecovered by naive approaches. *(Literature range ~20–48% of churn caused by failed payments, retry-only recovery ~12–18%: [ASSUMPTION] — cite Recurly/Zuora public benchmarks in `docs/` before pitch.)*
- Recovered revenue is ~100% margin — it's the cheapest revenue a merchant can acquire.
- Spam cost is real: complaints, DND/compliance exposure, churn of annoyed customers.

## 4. Why Now

1. **LLM reasoning is now cheap** enough to diagnose messy Indian bank decline strings and write genuinely vernacular (Hinglish) messages at per-message costs of paise.
2. **India rails make it acute:** UPI AutoPay and e-mandate recurring debits are mainstream; their failure modes (de-authorization, per-mandate caps, insufficient funds at debit time) are recovery problems at national scale. `[VERIFIED]` UPI AutoPay/eNACH are real NPCI products.
3. **Agentic infrastructure matured:** tool-calling, structured outputs, and policy evaluation are standard practice.
4. **The buildathon's Track 03 bar** (measured ₹ recovered, compliant escalation, stopping rules, audit trail) is precisely the rigor gap between shipped one-liners and a real product.
5. `[ASSUMPTION — verify before citing]` Razorpay has publicly announced agentic recovery tooling (Subscription Recovery Agent, Intelligent Retry Engine). If verified: Reflex is the **measured, merchant-side, root-cause-specific layer above it** — complementary, not competitive.

## 9. Core User Journey (Ananya, day one)

1. **Connect (5 min):** sign in → point Reflex at her Razorpay **test-mode** credentials → webhook URL registered → import customer context (simulated for demo) → set guardrail defaults (caps, quiet hours, daily budget ₹5,000) → choose **Advisory mode** first.
2. **Observe (day 1):** failures stream in → diagnosis chips appear → actions proposed with EV rationale → she approves a few, watches others auto-run under thresholds → ledger fills.
3. **Trust (day 2):** switches to **Autonomous mode** (still bounded) → watches recovered-₹ counter vs. naive-baseline counter diverge.
4. **Verify (day 3):** opens the Results tab → three-arm comparison, ablations, cost-per-₹100, complaint rate, one-command reproduction.
5. **Intervene as needed:** one complaint arrives mid-episode → Reflex auto-suppresses the customer and files a human-handoff → she resolves it from the approval queue.

## 15. Agentic Requirements

**Claim:** the Episode Agent is a genuine bounded agent — not a workflow labeled "agent." Justification against criteria:

| Criterion | How Reflex meets it |
|---|---|
| Planning | Bounded horizon-1: enumerate candidate interventions, rank by EV, schedule time-shifted top action. **Deliberate design (ADR-002, TechSpec §20):** open-ended multi-step planning is inappropriate for money actions; horizon-1 + observation loop achieves the same adaptivity with auditable decisions |
| Tool use | Allowlisted tools only: RP-TM create order, RP-TM payment link, channel sims, ledger write, policy read, suppression write |
| State | `episodes` + `actions` (AppFlow §14 state machines) |
| Memory | Episode-scoped (contact history, prior outcomes); customer-scoped (propensity features, suppression); policy-level (learned params) |
| Decision-making | EV policy (AI-2) within Shield constraints |
| Verification | Shield (pre-dispatch), message validator (AI-3), outcome attribution (FR-015) |
| Recovery | LLM outage ⇒ degraded mode; executor timeout ⇒ backoff ×3 ⇒ park + alert |
| Escalation | Human approval queue (value/pause/complaint triggers); ALWAYS for pause/cancel-class |
| Human approval | FR-012 gates; timeout auto-declines (fail-closed) |
| Action boundaries | Caps: 4 actions/episode, 2 contacts/customer/day, ₹5,000/day budget, quiet hours 21:00–09:00 IST, suppression list, kill switch |
| Stop conditions | RECOVERED · EXPIRED (72h) · cap reached · EV < 0 (STOPPED_LOW_EV) · complaint/opt-out (STOPPED_CUSTOMER) · kill switch (HALTED) · approval declined |
| Audit trail | Hash-chained action ledger, every state change |

**Deterministic components explicitly NOT called agents:** Shield, executors, ledger, replay engine.

## 17. Security & Trust Requirements

1. Webhook HMAC verification (`X-Razorpay-Signature` `[VERIFIED header]`); invalid ⇒ 401 + security event.
2. RBAC: `viewer` (read-only) / `operator` (controls) / `approver` (queue) / `admin`. Server-side enforcement only.
3. Secrets via environment, never in repo; test-mode keys only.
4. PII minimization: pseudonymous customer IDs, masked VPAs/cards; **no PII in LLM prompts or logs**.
5. Rate limiting on all API routes; idempotency keys on every mutating endpoint.
6. Hash-chained ledger + `/api/ledger/verify` endpoint.

# Rules — Reflex Development Constraints

**Version:** 1.3 · **These rules are non-negotiable.** They apply to every human contributor and every AI coding agent working on this repo. Violations = PR rejection, no exceptions. When in doubt: **fail closed, log everything, label simulations.**

> **v1.1 SYNC NOTE:** The rules themselves are unchanged and remain the bar. §18 maps each
> rule to its CURRENT enforcement/verification state in the codebase so the docs cannot imply
> compliance that has not been proven. Partial ≠ acceptable-end-state; those gaps are tracked
> in `6. ImplementationPlan.md` / `7.Tracker.md`.

---

## 1. Security Rules

1. Never commit secrets, keys, tokens, or `.env` files. Gitleaks runs in CI on every push **including history**.
2. Server-side authorization is mandatory. UI hiding is cosmetic. Every route enforces RBAC (viewer/operator/approver/admin) — matrix-tested.
3. Never trust client input: Pydantic validation at every boundary; webhook raw body HMAC-verified **before** parsing.
4. Rate-limit every API route per TechSpec §10. Idempotency keys required on all mutating POSTs.
5. Log every security event (401s, blocked dispatches, kill-switch use, chain-break) as structured JSON.
6. No CORS wildcards. No `DEBUG=true` in committed configs.
7. Test-mode Razorpay keys only. **Live keys are forbidden in this project, period.**
8. PII never enters prompts or logs. Pseudonyms + masked instruments only. Scanner test enforces.

## 2. AI Safety Rules

1. **Never trust raw LLM output.** Every LLM response passes schema validation before use. Invalid ⇒ one retry ⇒ deterministic fallback. Never a third guess.
2. **The LLM never authors money-bearing content.** Amounts, links, deadlines, UPI handles, dates are DB-injected into slots **after** generation. The validator must reject 100% of digit/URL/₹-bearing generated spans (CI-enforced corpus), including spelled-out number/currency words (Hinglish + English wordlist).
3. **The LLM never executes anything.** It can only produce structured proposals consumed by deterministic code. No dynamic tool selection outside the fixed allowlist.
4. Treat every untrusted field (bank strings, replies) as **data, not instructions**: `<data>` wrapping, instruction contract in system prompt, injection corpus in CI.
5. Confidence < 0.6 ⇒ conservative default (UNKNOWN_AMBIGUOUS path). Never act boldly on low confidence.
6. Log every LLM call: purpose, prompt hash, redacted input, output, validity, latency, cost, model.
7. Prompt templates are versioned artifacts in `packages/prompts`; prompt changes require an eval-suite run in the PR.
8. If AI output would cause an action the deterministic path wouldn't permit, the deterministic path wins. Always.

## 3. Agent Rules

1. The Episode Agent has one responsibility: drive its episode to a terminal state within bounds. No cross-episode autonomy, no global actions.
2. Tools are allowlisted in code (TechSpec §8). Adding a tool requires an ADR + Shield review.
3. Every action must pass Shield **at dispatch time** (state may change between planning and dispatch).
4. Bounds (hard, non-overridable): 4 actions/episode · 2 contacts/customer/day · ₹5,000/day budget · quiet hours 21:00–09:00 IST · suppression list · value > ₹50,000 ⇒ approval · pause/cancel-class ⇒ approval, always.
5. Stop conditions are mandatory and terminal: RECOVERED / EXPIRED / CAP / LOW_EV / CUSTOMER / APPROVAL_DECLINED / HALTED. Once terminal, never reopened (re-fail ⇒ new episode).
6. Uncertainty ⇒ escalate, never improvise: unknown diagnosis ⇒ conservative default; executor failure ⇒ park; anything ambiguous with money implications ⇒ human queue.
7. The agent must be able to explain every action from persisted data alone (EV breakdown + guardrail snapshot + policy version). If it can't, the design is wrong — fix the persistence, don't add narration.

## 4. Financial Safety Rules

1. **No irreversible money movement in MVP.** Executors may create RP-TM orders/links and send `[SIMULATED]` messages. Nothing else. Refunds/transfers/cancellations: forbidden.
2. Idempotency keys are mandatory on every dispatch; duplicate execution must be impossible at the DB level (unique constraint), not merely unlikely.
3. Ledger-first invariant: an action that cannot be ledgered must not be dispatched.
4. Every human-facing action shows the Action Preview Card: WHAT / WHY / IMPACT / RISK / GATE / APPROVAL / REVERSIBILITY (Design §15).
5. Fail closed: approval timeout ⇒ decline; budget uncertainty ⇒ stop paid actions; ledger failure ⇒ halt dispatch; DB loss ⇒ 503 ingestion.
6. Kill switch must work under any state, drain in ≤ 1s, and require deliberate re-enable.
7. Rollback story for every action class documented in `docs/safety.md` before that class ships.
8. B1 baseline must be **honestly tuned** (documented search). A strawman baseline is a integrity violation, not a tactic.

## 5. Database Rules

1. All money is paise (BIGINT). Never floats. Formatting to ₹ happens client-side only.
2. Enums are DB enums; no free-text statuses.
3. `action_ledger` is append-only — app role has INSERT/SELECT only; no UPDATE/DELETE grants, verified by test.
4. Agent services use the `reflex_agent` DB role which **cannot read** `replay.sim_*`. Any PR that widens these grants is rejected.
5. Migrations are forward-only during the buildathon; every migration has a down-doc (notes), even if not executable.
6. Every foreign key explicit; every query that feeds the dashboard has an index (no seq-scans on hot paths — checked in CI explain test).

## 6. API Rules

1. Routes, auth, and error shapes follow TechSpec §10 exactly — it is the contract; changes require updating all 8 docs in the same PR.
2. Errors are structured: `{error: {code, message, action?}}`. Never leak stack traces.
3. Webhook endpoint returns 200 for duplicates; 401 only for bad signatures; never processes the same provider event twice.
4. SSE events are additive; renames are breaking changes requiring a version bump.
5. No endpoint may return `replay` hidden-truth data. Ever.

## 7. Frontend Rules

1. Follow `4. Design.md` tokens — no ad-hoc hex values, no non-scale spacing/radii.
2. All amounts: `formatINR` (Indian grouping, tabular nums). Never render raw paise.
3. Every simulated datum gets its `[SIMULATED]` badge; Razorpay surfaces get `[TEST MODE]`. No exceptions, including charts and exports.
4. No client-side authorization logic beyond cosmetic hiding.
5. Counters/drawers degrade gracefully on SSE loss (stale toast + timestamp), never blank.
6. Accessibility gates in CI: contrast, keyboard path for the core demo flow, aria-live on mode banners.

## 8. TypeScript Rules

1. `strict: true`; no `any` in `apps/web/src` (eslint blocks).
2. Types for API payloads are generated from Pydantic schemas (single source of truth) — never hand-duplicated.
3. Money/IDs are branded types (`Paise`, `EpisodeId`) — a paise value can't be rendered as a count.
4. No business logic in components: calculations live in `packages/core`-derived TS utils, unit-tested.

## 9. Error Handling Rules

1. Never swallow an exception. Every catch either handles, rethrows wrapped, or parks + alerts — with a ledger/log entry.
2. Executor failures: 3 backoffs (1s/4s/16s) then `parked` + alert. Never retry a Shield BLOCK.
3. Degraded mode is the universal LLM-failure answer; unknowns get conservative defaults, not guesses.
4. If any invariant feels uncertain → fail closed and surface to a human.

## 10. Logging Rules

1. `structlog` JSON with `trace_id`/`episode_id`/`action_id` correlation.
2. No PII, no secrets, no full LLM prompts (hash + redacted input only).
3. Every state change logs at INFO; every guardrail decision at INFO with reason; errors at ERROR with stack id.
4. Logs must let an auditor reconstruct any episode without the UI.

## 11. Testing Rules

1. CI must be green to merge: unit, integration, API+RBAC, AI suites, security, e2e golden path.
2. AI suites are **blocking regressions**: diagnosis ≥85%, validator 100%, injection corpus 100%, COMPLAIN precision ≥95% AND recall ≥90% offline. *(v1.2 audit P1-3: precision alone cannot prove the zero-post-complaint-contact promise; confidence-gated fallback for AI-4 tracked as TASK-054.)*
3. Shield tests are adversarial by design — include at-limit boundaries (exactly 4/4, exactly budget, exactly quiet-hour edge 21:00:00).
4. Any bug fix ships with the test that would have caught it.
5. `./reproduce.sh` on clean clone is part of release QA, not optional.

## 12. Performance Rules

1. Budgets per TechSpec §18; regressions >20% on p95 paths fail CI perf job.
2. LLM calls: cache-first (`code_raw×issuer`); never call the LLM when rules suffice.
3. No N+1 dashboard queries; SSE aggregates precomputed in workers.
4. Replay must finish 3×3,000+ablations in <10 min on the reference VM.

## 13. UI / Design Rules

1. Ship the design system, not one-off screens: new UI = existing tokens/components or a documented addition.
2. Trust patterns are mandatory wherever an action or AI decision appears (EV drawer, Preview Card, ledger).
3. The 60-second wow path must never regress — e2e script asserts counters, chips, drawer, outage banner.
4. Honesty is a UI feature: labels, CIs, modes, and timestamps are first-class, never tooltips-only.

## 14. Git / GitHub Rules

1. Trunk-based: short-lived branches → PR → squash merge; ≥1 approval or self-approval with recorded reasoning during buildathon.
2. Conventional commits; PR template includes tests + docs impact + demo impact.
3. Tag milestones: `eval-preregistered-v1` (must precede first results commit), `v1.0-submission`.
4. Never rewrite history after `eval-preregistered-v1`.
5. README is a deliverable, not an afterthought — kept current with every user-facing change.

## 15. Environment / Secrets Rules

1. Config via env only; `.env.example` documents every variable.
2. LLM provider/model is configurable; the system must run end-to-end (degraded or cached) with the LLM absent.
3. Demo environments must be rebuildable in ≤10 minutes from repo alone (`make up && make seed && make demo`).

## 16. Demo Integrity Rules — **ZERO TOLERANCE**

> **NEVER fake metrics, API responses, transactions, customer data presented as real, AI evaluation results, or integrations.**

1. Everything simulated is labeled `[SIMULATED]` in UI, ledger, exports, README, video. Channels: WhatsApp/SMS/email/voice are simulators; customer data is synthetic.
2. Razorpay integration runs in **test mode** and is labeled `[TEST MODE]`. Never imply live traffic.
3. All metrics come from committed, reproducible runs (protocol-tagged). Never type a number into a slide that isn't in `eval/results/`.
4. Failure demos must be real injections through the real system — never scripted UI fakery.
5. If something breaks live: say so, show recovery, move on. Honest failure > fake success. That's the brand.
6. `docs/limitations.md` lists what Reflex does NOT do and one cohort where it loses. Linked from README.

## 17. "DO NOT" Rules

1. ❌ Do NOT let the LLM output an amount, link, date, or UPI string — post-injection only.
2. ❌ Do NOT dispatch without Shield PASS + ledger write, in that order.
3. ❌ Do NOT bypass caps "just this once" — including for the demo.
4. ❌ Do NOT tune the simulator so Reflex wins; tune it to cited public patterns, then report what happens (ADR-007).
5. ❌ Do NOT make B1 a strawman.
6. ❌ Do NOT hardcode expected metric values into the agent or UI.
7. ❌ Do NOT read `replay.sim_*` from agent code (role-enforced + lint rule).
8. ❌ Do NOT add microservices, orchestration frameworks, or any architecture the demo doesn't need (ADR-001).
9. ❌ Do NOT add AI anywhere a rule already works (rules-first diagnosis is a feature, not a compromise).
10. ❌ Do NOT ship an unlabelled simulation, an unexplained number, or an unaudited action.
11. ❌ Do NOT touch live keys, real customers, or real channels in this project.
12. ❌ Do NOT cut Shield, ledger, baselines, degraded mode, labeling, or reproduce.sh — the MVP cut line is explicit (ImplementationPlan).
